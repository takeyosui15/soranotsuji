## 0. 一言サマリ

MSM(気象庁メソモデル)の気象場と地形(DEM)を多チャネル画像として小型U-Net(CNN)に入力し、雲海の出現確率マップを出力する。教師ラベルはひまわり衛星(千葉大CEReSアーカイブ)から自動生成する。データは毎晩自動で増え、訓練は「全データ再訓練+warm start」を定期実行する継続訓練方式。推論はGitHub Actionsで毎晩バッチ実行し、静的PNGとして宙の辻に重畳表示する。

```
[Open-Meteo MSM] ─┐              ┌→ [毎晩: 特徴量 npz] ─┐
[CEReS ひまわり] ──┼→ ラベル生成 ──┤                      ├→ [定期: 再訓練] → model
[GSI DEM]       ─┘   (毎晩)      └→ [labels npz+manifest]┘        ↓
                              [毎晩21:30: 明朝の推論] → 確率マップPNG + meta.json → gh-pages → 宙の辻
```

| D6 | 継続訓練は**増分学習ではなく全データ再訓練+warm start**。champion/challenger方式で昇格判定 | 破滅的忘却の回避・完全な再現性・この規模なら計算が安い |

| D9 | ラベル不明画素(上層雲で衛星から見えない等)は**0にせずlossからマスク除外** | 「見えない」と「無い」を混同すると学習が壊れる |

## 3. データ仕様

### 3.1 MSM(Open-Meteo)

- 実績(訓練用): `https://historical-forecast-api.open-meteo.com/v1/forecast?models=jma_msm&start_date=...&end_date=...&hourly=...&elevation=nan&timezone=Asia%2FTokyo`
- 予報(本番推論): `https://api.open-meteo.com/v1/forecast?models=jma_msm&...&elevation=nan`
- 予報(v2訓練用): Previous Runs API の `_previous_day1` 系列(有効時刻の24時間前初期値)
- 格子仕様: 地上要素 0.05°(約5km)・1時間値 / 気圧面要素 0.1°(約11km)・元3時間値をAPIが1時間に内挿
- 取得方法: bbox内を0.05°刻みの点リストにし、`latitude`/`longitude` にカンマ区切りで一括指定(1リクエスト約100点で分割)。※APIドキュメントUIに「Bounding box」指定が存在するので、**先に対応可否を確認し、使えるならそちらに置換**
- hourly変数(v1確定):
  - 地上: `temperature_2m, dew_point_2m, relative_humidity_2m, cloud_cover, cloud_cover_low, cloud_cover_mid, cloud_cover_high, pressure_msl, wind_speed_10m, wind_direction_10m, precipitation, shortwave_radiation`
  - 気圧面(1000/975/950/925/900/850 hPa): `temperature_*, relative_humidity_*, dew_point_*, wind_speed_*, geopotential_height_*`
- レートと礼儀: 非商用枠は約1万コール/日。**日付単位のローカルキャッシュ必須**(取得済みはスキップ)、指数バックオフ、User-Agent明記
- ライセンス: Open-MeteoはCC BY 4.0。アプリのクレジットに表記を追加
- **スケール上の注意: 本APIは地域bbox前提の道具。全国展開時は訓練用途に使わないこと(→ 末尾の追記)**

### 3.2 CEReS ひまわり8/9 グリッドデータ

- 入口: anonymous FTP `hmwr829gr.cr.chiba-u.ac.jp`(観測1日後以降のデータがフリー)
- **最初にFTPルートのREADME/フォーマット文書を取得し、ディレクトリ構造・ファイル命名規則・DN→物理量(輝度温度/反射率)変換テーブルを確認すること。**本仕様は概要のみ規定する:
  - TIR(0.02°≈2km、6000×6000、バンド07: 3.9µm / バンド13: 10.4µm): 夜間の霧判別、頂面輝度温度
  - EXT(0.005°≈約0.5km、24000×24000、バンド03可視): 日中の面確認・高解像度ラベル
  - SIR(0.02°、バンド05: 1.6µm): 積雪と霧の分離(雪は1.6µmで暗く、水雲は明るい)
  - 座標系: 緯度経度直交(EQR)、カバレッジ 85E–205E / 60S–60N。画素↔緯度経度は線形計算
- 取得時刻(JST): 各朝 **03:00〜08:00 を30分刻み**(約11スロット)。10分刻みへの精密化はv2
- **ダウンロード後ただちにbboxで切り出し、元ファイルは削除**(フルディスクEXTは1スロットGB級)。切り出しは npz(uint16 DN+変換テーブル参照)で保存
- 帯域配慮: 逐次1コネクション、夜間バッチ、リトライ間隔は長めに
- 謝辞: 成果公表時はCEReS所定の謝辞文を記載(READMEの文言に従う)。営利利用は不可(気象庁ポリシー)

### 3.3 DEM・地形特徴量(静的、1回だけ生成)

- 入手: GSI標高タイル(宙の辻の既存RGBデコーダを流用)
- 学習格子(1km)向けに事前計算: `elev_mean, elev_min, elev_max, TPI_2km, TPI_10km`(地形位置指数=自セル標高−半径内平均)、`valley_depth`(半径5km内max−自セル)
- flood fill用に細解像度の `elev_fine`(100〜250m格子)を別途保存

## 4. ラベル生成アルゴリズム(擬似コード)

対象: 各朝 T ∈ {05:00, 06:00, 07:00 JST}

```
1. 霧/下層雲マスク(2km格子):
   夜間・薄明:  BTD = TB(B07) − TB(B13) ≤ −2.0 K → fog候補   # 初期閾値。Phase 0で調整
   日中:       EXT反射率 ≥ 0.35 かつ TB(B13) ≥ (MSM t2m − 5K) → fog候補
               # 雲頂温度が地表気温に近い=低い雲、の判定
   冬期:       SIR B05反射率が低い明域は積雪として除外
2. 観測不能マスク:
   MSM cloud_cover_high > 60% または TB(B13) < 253K
   → その画素は「ラベル不明」。0にせず、loss計算から除外(D9)
3. 頂面高度 h:
   fogマスク内の TB(B13) の中央値 T_top を取り、
   最寄りMSM格子の気温プロファイル T(z)(気圧面T + geopotential_height)を
   **地表側から上方に**探索、最初に T(z)=T_top となる高度を h とする
   # 逆転層で同じ温度が2高度に現れるため必ず地表側から
   解が範囲外なら h=NaN(品質フラグ)
4. 面展開(flood fill):
   elev_fine 上で、fog画素直下の谷底セルを種とし、
   条件 elev < h の8近傍連結成分を塗る → 500m格子に集約
5. ソフトラベル化:
   1km格子ごとに被覆率(0.0〜1.0)を算出。
   品質フラグ(qc_highcloud, qc_h, qc_daynight)と共に labels/YYYYMMDD_HH.npz 保存、
   manifest.csv に1行追記
6. QA: ラベル・EXT画像・DEM陰影を並べたPNGを吐く qa_report.py(毎晩の成果物)
```

## 5. 特徴量テンソル

- 学習格子: 1km、bbox、約68×61 → パディングして **72×64**
- 時刻: ラベルと同時刻のMSM値(v1)。前夜スナップショットの追加チャネル化はv2
- チャネル(初版18ch、`configs/features.yaml` で増減可能に):
  - 気象12: `t2m, td2m, (t2m−td2m), rh2m, u10, v10`(風向風速から変換)`, cloud_low, cloud_mid, cloud_high, (T925−T1000)`[逆転指標]`, RH950, 前日18時からの降水積算`
  - 地形4: `elev_mean, TPI_2km, TPI_10km, valley_depth`
  - 時期2: 日付の周期エンコード `sin(2π·doy/365), cos(2π·doy/365)`(季節性の事前情報。→追記4)
- 補間: MSM点群(5km/11km)→1km は bilinear。時間方向は正時取得のため補間不要
- 正規化: z-score。**統計は訓練期間のみから算出**して `norm_stats.json` に保存、推論でも同一のものを使う
- 保存: `features/YYYYMMDD_HH.npz`(float16可)

## 6. モデル・訓練・評価

- フレームワーク: PyTorch
- U-Net: encoder 3段(16/32/64ch)、GroupNorm、出力1ch+sigmoid。約0.3Mパラメータ
- Loss: masked BCE(ソフトターゲット、pos_weight自動算出)。不均衡が強ければfocalに切替可能な実装
- データ分割: **時間分割**。テスト=直近1シーズンを丸ごと凍結(例: 2025-10-01〜2026-04-30)、検証=その前年シーズン、訓練=残り全部。同一朝の3時刻は必ず同一split(リーク防止)
- ベースライン(**CNNより先に実装し、必ず比較表に載せる**):
  - B0: 気候値(画素×月の出現率)
  - B1: ルールベース雲海指数(宙検索のスコアリング思想の応用)
  - B2: 画素独立ロジスティック回帰(同じ16chを入力)
- 指標: PR-AUC(主指標)、IoU@0.5、Brierスコア、竹田城画素のヒット率/誤報率、信頼度図。校正が悪ければ温度スケーリング
- 乱数シード固定、設定はyamlに一元化、学習曲線と評価表をmarkdownで自動出力

## 7. 継続訓練の仕組み(発注者の明示要望)

原則: **増分(オンライン)学習はしない。** データが増えるたびに全データで再訓練し、前回重みからのwarm startで時間短縮する。理由: 破滅的忘却の回避、完全な再現性、この規模ならCPU数時間以内で回ること。MSM側のモデル更新による分布ドリフトも、定期再訓練が自動的に吸収する(副次効果)。

### 7.1 毎晩ジョブ `nightly_data`(GitHub Actions、cron 22:00 JST頃)

1. 前日朝のCEReSデータ取得 → ラベル生成 → QA画像
2. 同朝のMSM実績取得 → 特徴量生成
3. manifest更新、データリポへcommit
4. 失敗日はmanifestに欠測として記録し、翌晩リトライ(最大7日遡り)。CEReSは1日遅れ公開なので「前日分」処理が基本

### 7.2 再訓練ジョブ `retrain`(手動トリガ+毎月1日自動)

1. manifestのハッシュでデータセットに版番号を付与
2. 訓練 → 凍結テストで評価
3. champion(現行)とchallenger(新版)を同一テストで比較し、**主指標が改善した場合のみ** `models/registry.json` を更新して昇格
4. 比較レポート(md)を自動生成してcommit

### 7.3 毎晩ジョブ `nightly_infer`(cron 21:30 JST)

- 現championモデルで明朝05/06/07時を推論 → `unkai_YYYYMMDD.png`(確率カラーマップ+アルファ)+`meta.json`(bbox、モデル版、生成時刻)→ gh-pagesへ
- 翌晩、予報と実績ラベルの照合結果を自動追記(**運用そのものが評価データを生む**)

## 追記(2026-08-04): 全国展開時のデータ取得方式

Open-Meteoの点APIは**地域bbox前提の道具**である。無償枠は約1万コール/日で、長期間・多変数のリクエストはデータ量に応じて複数コール分として重み付き計上される。

- 地域版(現仕様 ≈190点 × 朝時間帯 × 8年): 一括バックフィルは行儀よく分割しても数日〜2週間規模 → **問題なし**。毎晩の増分は誤差レベル
- 全国(MSM格子で日本の陸上 ≈1.5万点 × 同条件): 総取得量は数十億値のオーダーとなり、無償枠を使い切り続けても**年単位** → 点APIでは実質不可能、かつ提供元への迷惑になる

**全国展開の判断が下りた場合**は、訓練側のデータ取得を京大RISH(生存圏研究所)のMSM GRIB2/NetCDF直取りに差し替える。1日分=数ファイルのダウンロードで全国格子が丸ごと手に入り、1.5万回のAPI呼び出しが1回のファイル取得に置き換わる。設計上の整合は保たれる:

1. 同じMSMなので**D1(訓練・本番の分布一致)は壊れない**。むしろ補間前の生格子値であり、D8(`elevation=nan`で生格子に近づける)の意図の理想形になる
2. 実装は `src/fetch_msm.py` の交換で完結させること(このための分離である)
3. 保存は5km原寸(npz等)とし、1km化は学習パッチ生成時に**遅延補間**する(全国1kmテンソルの事前展開は数百GBになるため不可)
4. **訓練ソースを混在させない**: バックフィルと日次増分は同一ソース(RISH)に統一。切替時はOpen-Meteo値との突合検証(同一地点・同時刻のRMSE確認)を1回実施する
5. 本番推論の入力は引き続きOpen-Meteoでよい(夜間1回の全国予報取得は、変数と時刻を絞れば枠内に収まる)
6. RISHは研究・教育目的向けの厚意で運営されている。逐次ダウンロード・夜間実行・帯域配慮を厳守すること

## 追記2(2026-08-04): RISHデータの権利・保管容量・増分運用

### A. 権利(入口)

- RISHアーカイブは**教育・研究目的向けの無償二次提供**(元は気象業務支援センター経由の気象庁データ)。商用利用不可。成果公表時は同データベースを利用した旨を謝辞に明記。大量一括取得を避け帯域に配慮する
- **学習への利用(消費的利用)と、データの再配布は別物として扱う。** GRIB原本、および実質等価な準生データ(広域・全変数のnpz等)をパブリックリポジトリで再配布しないこと
- 公開してよい成果物: コード、モデル重み、正規化統計、manifest、高加工の派生物(雲海ラベル、評価レポート、出典明記した少数のQA画像)
- 位置づけに迷いが生じた場合は、用途を添えてRISH窓口に確認する(発注者タスク)

### B. 保管容量の設計

| 対象 | 概算 | 置き場 |
|------|------|--------|
| 生GRIB(夜間取得分) | 60〜150MB/夜 | 抽出後ただちに削除(保持しない) |
| 特徴量npz(地域v1) | 8年で1GB弱 | データリポ(private)可 |
| 特徴量npz(全国) | 数十GB級 | **gitに置かない。**ローカルSSDのキャッシュ扱い |
| ラベル(圧縮) | 全国でも1GB級 | データリポ(private)可 |
| モデル・統計・manifest | MB級 | unkaiリポ本体 |

- 原則: **特徴量は「manifest+コード+RISH」から決定的に再構築可能なキャッシュ**であり、アーカイブすべき真実はmanifestとコードの側にある。GitHubの実務制限(1ファイル100MB、リポジトリ推奨1GB、LFS無料枠約1GB)はこの設計なら問題にならない

### C. 増分運用

- 毎晩ジョブのRISH版: 前日朝分の該当初期値(2ラン)のLsurf/Lpres GRIBを取得 → 必要時刻・変数を抽出 → npz化 → 原本削除 → manifest追記 → ラベルと突合
- 実行場所: 地域版はGitHub Actionsで完結可。全国版は常設ローカル機のcronで実行し、**軽いもの(manifest・ラベル・レポート)のみpush**する分業とする
- RISH側の欠測・遅延は正常系として扱う(台帳に記録、最大7日遡りリトライ=既存設計と同一)
- **年1回の再構築検証**: 任意の1週間分をmanifestからゼロで再導出し、hash一致を確認するCIジョブを設ける。生データを自前で永久保管しない設計に対する再現性の保険
- MSM仕様変更(変数追加・格子変更・モデル更新)はパーサで検知したらジョブを停止しQAレポートに出す。manifestにはソース版タグを持たせる

### D. 出口の規制(データライセンスとは別軸)

- 独自の気象予測を**反復・継続して一般に公開する行為**は、気象業務法上の「予報業務」(要許可)に該当し得る(無償でも)。自己利用・限定利用であれば不要
- 方針: **Phase 4は発注者自身用(非公開ないし限定URL)として実装**し、一般公開の判断はQ5として保留する。一般公開する場合は、事前に気象庁(最寄りの管区気象台)へ該当性を確認すること
- アプリ内の既存表示(気象庁発表の予報・観測値の転載や解説、宙検索のような公表データの加工表示)はこの論点の対象外

## 追記3(2026-08-04): 週末計画モード(中期予測)の要件追加

### 要件の再定義

- 主ユースケース: **水曜〜金曜の時点で週末(土日朝)の雲海チャンスを判断し、周囲と予定を相談できること**。前夜Go/No-Go・未明確認は最終段として維持
- 設計思想: 単発の予報ではなく、**日々更新で確率が絞られる「漏斗」**として提示する(水: 傾向 → 木金: 具体化 → 前夜: 判定 → 未明: 確認)

### 予報範囲の物理的境界(JST)

- MSMの予報範囲は最長78時間(00/12UTC初期値のみ。他は39時間)
- 土曜朝5時: 水曜21時初期値で+56h → **水曜夜からMSM圏内**
- 日曜朝5時: 木曜9時初期値で+68h → **木曜昼からMSM圏内**(水曜時点では圏外)
- それより先(水曜時点の日曜など)はGSM(0.5°格子・6時間値、Open-Meteoで11日先まで)の担当

### モデル設計

- 短期モデルを拡張し、**リードタイム(時間)を条件チャネルとして入力する1モデル構成**とする。day1〜5の訓練サンプルを共有できる(ガイダンスの定石)
- GSM入力の中期用は**別写像 h_GSM として学習**(D1の分布一致原則をGSM側にも適用)。出力格子は同じでよいが、UIでは校正済み確率を3段階(有望/微妙/望み薄)に丸めて表示
- **訓練データは最初からPrevious Runs APIの該当リード系列を使う。** 短期版のD5例外(準解析値で代用)はリード数時間だから許容できたのであり、リード3〜5日では予報誤差そのものが信号の本体となるため代用不可
- 入力系列: 対象朝を終端とする**直近24〜36時間の系列**(GSMは6h刻み5〜7フレーム、MSMは3h刻み)+先行期間の要約チャネル(積算降水等)。5日分全フレームの投入はConvLSTM等と併せてv2以降の検討事項
- 10分間隔の予報データは存在しない(10分は衛星観測側の刻み)。入力の時間解像度は予報プロダクトの刻みが上限

### 評価と期待値管理

- リード3〜5日の霧の「的中」は現業機関でも困難。目標は**気候値に勝つ校正済み確率**とし、評価にリード別のBrier skill score(対気候値)と信頼度図を追加
- 実用の第一線は「明確に望みのない週末の除外」と「有望週末の検知」。気圧配置スケールの現象なので、このリードでも予測可能性は十分にある
- UI: 週末カレンダー形式で日別確率と更新履歴(漏斗の推移)を表示する

### スケジューリングの注意

- cronは数分〜十数分のジッタ・稀な取りこぼしがある前提で設計(ファイル名は実取得時刻、欠測は正常系)
- **カメラcronは月指定で季節を織り込む**: `*/10 19-22 * 1-4,9-12 *`(UTC。JST 04:00〜07:50、1〜4月と9〜12月のみ実行。月境界の±1日ズレは許容)→ **毎シーズン自動で再開・停止**し、来期以降の手作業ゼロ

- 今期の特別性は「最初の凍結評価セットと衛星ラベラー校正の土台になる」点のみ。来期以降は定常運用

### 既知の不確実要素(Phase C試運転で判定)

- **YouTubeはデータセンターIPからの取得をbot判定で弾く場合がある**(近年強化傾向)。高梁(YouTubeライブ)のみの懸念で、竹田城(静止画curl)には無関係

## 追記6(2026-08-04): リードタイム階梯 — 週末プランニング対応(追記3の詳細化)

**背景**: 発注者の本来の利用シーンは「水〜金曜のうちに、土日朝の雲海可能性を仲間と相談する」こと。前夜判断(v1)はその最終段に過ぎない。

### 原則

1. 入力は常に「**対象の朝についての予報値**」。過去実況の高頻度化(10分/3時間サンプリング)はD-4予測に寄与しない(放射霧の記憶は短く、中期の可否は総観場=全球モデル内の情報が決める)。10分データの用途はラベル生成のみ
2. **リードタイム別に別モデル**を訓練する(D-1 / D-3 / D-4-5)。訓練データはPrevious Runs API の `previous_dayN` 系列を用い、各リードで訓練・本番の分布一致(D1原則)を保つ
3. ラベル(ひまわり由来)は**全リード共通**。ラベル資産への投資は自動的に全段で再利用される

### 物差しの時刻表

| 判断タイミング | 土曜朝 | 日曜朝 |
|---|---|---|
| 金曜夜 | MSM 39h(v1そのまま) | MSM 78h |
| 木曜夜 | MSM 78h | MSM 78h(00/12UTC初期値) |
| 水曜 | MSM 78h | **+80h=MSM圏外(2時間超過)→ 全球モデル** |

- 全球モデル候補: GSM(0.5°・6時間値・Previous Runs 2018〜)/ ECMWF IFS(0.25°・アーカイブは2022年頃〜)。6時間値の粗さは「チャンス度」粒度なら許容。Phase 2(v3)で両者を比較評価する
- 参考: アンサンブル予報(スプレッド=不確実性の物差し)はv3以降の検討事項

### 出力仕様(中期段)

- 点予報のふりをしない。**チャンス度%+3段階(◎○△)+前日からの推移矢印**で表示(例: 「日曜: 60%→75%↑」)
- UIは「週末に近づくほど解像度が上がる」段階表示: 水=チャンス度(広域)→ 木金=確率マップ(5km→1km)→ 前夜=v1の面予報
- 評価はリード別に別表(D-4のPR-AUCがD-1より低いのは正常。低下カーブ自体を成果物として記録する)

### v計画への反映

- **v1は不変**(前夜判断=全リードの土台。ラベル・検証環境を確立する)
- v2 = D-3(MSM 78h、`previous_day2/3`で訓練)
- v3 = D-4/5(全球モデル入力、別写像。GSM vs ECMWF比較を含む)

## 追記7(2026-08-04): 高山雲海への一般化・出力刻みの確定・副産物(雲断面ビュー)

### 目的の一般化

- 予測対象を「谷の放射霧」から**「観測点より低い高度に雲頂を持つ雲層」へ一般化**する。谷霧型(竹田城・備中松山城、h≈200〜500m)と高山層雲型(北アルプスの山小屋、h≈1,500〜2,500m)は、同一の枠組み(頂面高度h × DEM交差判定)で扱える。flood fill/水たまりモデルは観測者非依存であり、コア設計の変更は不要
- 気圧面の使用層は**観測点標高に依存して下から選ぶ**。全国・高山対応の実質範囲は1000〜600hPa(燕岳級では850〜700hPaが主役)。500hPaより上は雲海の主役ではなく、衛星視線・観測者視界を遮る**上層雲の検知チャネル**(D9のマスク判定)として引き続き使用
- 高山層雲型は総観規模の現象であり、谷霧型より長リード(3〜5日)の予測可能性が高い → 週末計画モード(追記3・追記6)および実需要(山小屋予約の事前判断)と相性が良い
- スコープ: **v1は谷霧型(高梁)のまま不変**。高山型は全国展開(RISH切替)時に対象化。山小屋系ライブカメラ(燕山荘など。存在・規約は要確認)を高山側のアンカー候補として記録

### 出力の時間刻み(発注者サマリの訂正)

- **予報マップは1時間刻み**(明け方〜8時)。10分刻みの予報データは存在しない(10分はひまわり観測側の解像度)
- ひまわり10分値は**「当日の実況モニタ」画面**(予報ではなく現況表示)として別途活用する。実況表示は予報業務該当性の観点でも安全側(追記2-D)

### 副産物: 雲の鉛直断面ビュー(ML不要・先行実装可能)

- 気圧面16層×1時間の雲量(湿度由来のSundqvist近似)を時間×高度で描画すれば、任意地点の**雲断面時系列**がクライアントサイドで描ける(Open-Meteo気圧面APIの直接可視化)
- 位置づけ: ①モデルの説明・QA画面(「湿った下層+乾いた上層+逆転の蓋」を見せて予測根拠を示す)②山行計画ツール(雲頂が山小屋標高を下回る時間帯が一目で分かる)③**以前構想したMapLibre GL JS fill-extrusionによる大気3D断面の具体化**(まず2Dの時間×高度断面から)
- 実装地位: MLに依存しないため**Phase 0と並行して先行実装可**(宙の辻の新画面候補)。気圧面cloud_coverが診断値である旨の注記を画面に付す

## 追記9(2026-08-04): 命名の確定と④「宙統計」の仕様骨子

### 命名確定(発注者決定)

- ① **宙断面** ② **宙メッシュ検索**(本ファイル全体の表記を更新済み)③ **メッシュunkAI** ④ **宙統計**(本追記で定義)

### 宙統計の目的

- 気象の**気候値(平年傾向)**を日付×時刻×層×地点で提供し、「この時期のこの日は晴れやすい」を月〜年スケールの計画(山行・遠征・定年後の平日行)に使えるようにする
- 漏斗の最上流(リード∞)として位置づけ: **宙統計 → 週末モード → 前夜 → 実況**の一気通貫が完成する
- データはunkAIバックフィル(RISH MSM 約20年 / Open-Meteo 2018〜)の副産物であり、**追加取得コストなし**で構築(発注者の見立て通り)

### 統計設計の要点(発注者の懸念への回答)

- **n問題**: 日付単独の統計はn≈15で薄く、隣接日との差はほぼ標本ノイズ → **±7日の移動窓**で合算し n≈225/日付 を確保する(公的平年値と同じ発想。窓幅は設定可能)
- **灰色化問題**: 平均場は持たない・使わない。**分位と確率(例: P(下層雲量<25%))で保持**し、宙メッシュ検索との連携は**「サンプルごとに採点 → スコアを平均」**(score→aggregate)とする。評価関数は非線形のため、平均場を採点する順序(aggregate→score)では月光サンドイッチ等の条件が発火しない。E[score(天気)] ≠ score(E[天気])
- **天体は統計しない**: 月齢・視高度は年ごとに異なるが決定論的に未来計算できる(Astronomy Engine)。宙統計=**気象の気候値 × 対象年の天体の正確な計算**のハイブリッド(例: 「2027-11-03: 晴れ確率◯% × 当夜は新月」)
- **特異日の扱い**: 表示にサンプル数と信頼区間を併記。366日付の多重比較により偶然「特異」に見える日が必ず生じる旨を注記(「11月3日=晴れの特異日」伝説を自前データで検定可能になる)

### 実装骨子

- 生の日付×24h×16層×1km保存は数百GB規模となるため不可。**二層構成**とする:
  - **マップ層**: 月(または旬)× 時間帯 × プリセット指数の全国スコアタイルを事前生成(光害マップと同じ「前処理 → 静的PNGタイル」パターン)
  - **地点層**: 任意地点の日別(±7日窓)フル統計をオンデマンド計算し、**宙断面の「平年レイヤ」**として表示(その地点・その時期の典型的な空の断面)
- 統計母体はMSM 5km格子で保持し、1km化は表示時の地形考慮に留める
