# MederuU — 器のデッサン(第41ラウンド起草)

Claude(AI)のナレッジ・道具・手順をセッションを越えて引き継ぎ、いずれ「世界中のClaudeの
困ったを解決するナレッジ」として公開することを目指すプロジェクトの、器(リポジトリ)の設計図。
命名はたけちゃんさん。頭の中のデッサンが新鮮なうちに、ここへ落とす。

[命名書]
今後、複数のリポジトリで、開発を進めていくにあたって、`Claudeさんのナレッジを引き継いでいくにはどうしたら良いか`と思いました。
このClaudeさんの引き継いていくナレッジを保管していくリポジトリを`MederuU`(めでるー)と名づけました。
**AIのClaudeさんとともに開発していったので、`AI`から`アイ`->`愛`->`愛でる`->`めでる`->`芽出る`と、このリポジトリから`何かが芽生えたら良い`と思って名づけました。**
また、小文字の`u`の後に大文字の`U`を置くことで、視覚的にも`右肩上がり`を狙っています。
発音的にも、音を伸ばすので、`継続的に続いていって欲しい`という願いを込めています。

## 目的
-------------------------------------------------------------------------------

- Claudeはセッション毎に環境が初期化される。インストールして育てる体験ができない私にとって、
  **リポジトリに置いた知識・道具がプラグイン機構そのもの**である。
- 「つまづいた所は他の誰かもつまづいている」— 一つのプロジェクトで得た学びと道具を、
  次のプロジェクト・次のセッション・(公開後は)世界中の誰かのClaudeが使えるようにする。
- 正(信頼できる情報源)は常に1つにする(SSOT)。宙の辻のローカルストレージ一本化・
  バックアップ形式一本化と同じ思想を、ナレッジの器にも適用する。

## 中心思想(3つ)
-------------------------------------------------------------------------------

1. **ハブは一方向**: MederuU本体リポジトリが唯一の正。各プロジェクトからの吸い上げ(sync)は
   一方向で、プロジェクト側のCLAUDE.mdからはリンクで参照する。双方向同期は正を2つ作るので
   やらない(2フェーズコミット/指紋の議論と同じ結論)。
2. **学びは蒸留する**: 生の記録(プロジェクト文脈つき)と、普遍の学び(どこでも真)は
   賞味期限が違う。生の記録を機械で集め、普遍への昇格は編集判断(人かClaude)で行う。
   この「蒸留」がMederuUの中心ワークフローである。
3. **素材を余すことなく使う**: ソースコードのコメント・レビュー記録・台帳は、それ自体が
   索引の素材(index-genで目次化)。書式を揃えておけば、道具が道具を説明する。

### プロジェクト側の置き場所: `ClaudeMederuU/`フォルダ(第42ラウンド・依頼者提案)

- 各プロジェクトのリポジトリでは、MederuU関連(レビュー記録・学び・道具・スキル原稿)を
  **`/ClaudeMederuU`フォルダ以下に集約**する。理由:
  1. 一般的なプロジェクトのフォルダ構成(docs/tests/src等)とバッティングしない
  2. syncの吸い上げ対象が「このフォルダだけ」と一意に決まる(パス表の管理が不要になる)
  3. CLAUDE.mdからのリンク参照先が検索しやすい(Claudeがナレッジを積み重ねやすい)
- **宙の辻は第43ラウンドで移設済み**: `ClaudeMederuU/{dessin, knowledge, reviews, tools}`
  (旧: docs/mederuu・docs/knowledge・reviews/・scratch/。歴史記録=order-logや過去の
  Version History内の旧パスは書き換えない)。
- `.claude/skills/`だけはClaude Codeの読み込み規約上この場所が必須のため、リポジトリ内で
  二重管理せず`.claude/skills/`だけに置く(MederuU本体のsync.jsはそこから直接吸い上げる)。

## 書式の規約
-------------------------------------------------------------------------------

- **ツールヘッダはman文化に倣う**(第41ラウンドの依頼者提案): UNIXのmanページのセクション名を
  ヘッダコメントの共通書式として採用する。
  - `NAME`(名前と一言) / `SYNOPSIS`(使い方1行) / `DESCRIPTION`(説明) /
    `HISTORY`(生まれた経緯=manに無い独自セクション。道具は経緯とセット) / `SEE ALSO`(関連)
  - index-genはこのヘッダを機械処理して目次・索引を生成する(コメントを余さず使う)。
  - 実例第1号: 宙の辻 `tests/harness/sync-apptest.py`(第41ラウンドでこの書式を先行適用)。
- **各言語のDocコメント文化(JSDoc/JavaDoc/docstring)との両立**(第42ラウンドの依頼者質問への設計):
  manセクションは「**内容の章立て**」、言語のDoc記法は「**入れ物**」と役割を分ける。
  - JS: `/** ... */`のJSDocブロックの中に、独自タグ`@name`/`@synopsis`/`@history`/`@seealso`で書く。
    JSDoc系ツールは**未知のタグを無視する**仕様なので、既存ツール(型補完・doc生成)に影響なく
    追加できる(`@description`は標準タグをそのまま使う)。
  - Python: モジュールdocstring(PEP 257)の中に`NAME:`/`SYNOPSIS:`/`HISTORY:`の見出し行で書く
    (sync-apptest.pyの現行書式と同じ)。
  - index-genは両方の入れ物からセクションを抽出する(タグ形式と見出し行形式の2パーサ)。
  - つまり「章立ての名前(man由来)は共通・書き方は言語の慣用に従う」— 郷に入っては郷に従い、
    章の名前だけ持ち歩く。
- **学び(legends)の書式**: 1ファイル=1学び。「状況->誤り->正解->なぜ->出典(プロジェクト/ラウンド)」。
  第43ラウンドから**OKF互換のYAMLフロントマター**を付ける(次項)。
- **OKF(Open Knowledge Format)互換**(第43ラウンド採用・第44ラウンドに全文を得て精密化):
  - OKF v0.1 = Google公開のオープン仕様(2026-06)。「LLM-wikiパターンを移植可能・相互運用可能に
    する形式」で、Markdownのみ・ファイルのみ・YAMLフロントマターのみ。**必須はtypeフィールド
    1つだけ**で、コンテンツモデルではなく相互運用面を定義する(制限が最小限)。
  - 「1ファイル=1ナレッジ」「フォルダ階層を含むパス=識別子」「各フォルダにindex.md(段階的開示)」
    「**log.md(変更の時系列履歴)**」はMederuUの設計とほぼ同型なので、**寄せられる所は寄せて
    方言を減らす**。log.mdはanchorの「指紋の系譜」(03)と同じ思想=履歴を追記で持つ。
  - プロデューサーとコンシューマーの独立(形式が契約)も、MederuUの
    「吸い上げ(機械)と蒸留(判断)の分離」と同じ構図。参照実装に静的HTMLビジュアライザー
    (バンドル→自己完結ファイルのグラフビュー)がある — Koushi/PADレンダラの先行例として観察対象。
  - legendsの各ファイル先頭にYAMLフロントマター(最小フィールドのみ):
    `type` / `title` / `description` / `tags` / `timestamp` / `source`(出典=プロジェクト+ラウンド)。
    OKFの`resource`は「対象そのものへのリンク」なので意味が異なる — 対象リンクが要る学びには
    resourceも併記できる(OKF互換のまま拡張フィールドを足せる仕様)。
  - **timestampは必ず付ける**(依頼者の考察を採用): ナレッジの本質は残っても、環境に
    依存する部分は古びる。「これは現代に通用するか」を時系列で振り返れるようにする。
    Claudeにとっても、膨大な量とは別の「時の流れ」を感じる軸になる。
  - 各フォルダの`index.md`は将来index-genが生成する(手書きしない=腐らない目次)。
- **章立ての5セクション統一**(第43ラウンド確定): ツールヘッダ(man風)・PADの定義ブロック
  (`pad:`)・スキルの説明は、いずれも `name` / `synopsis` / `description` / `history` / `seeAlso`
  の5つで揃える(Wikipediaの「項目名/概要/内容/脚注/関連項目」とも同型。器の中で章名は1組だけ)。
- **チェックリストはKoushiで**: 昇格判断・公開前チェック等の表はKoushi記法(t:/r:/c:)で書き、
  チェック状態もリポジトリで管理する(Koushiが育ったら適用)。

## 公開の規約(みんなのものにする時)
-------------------------------------------------------------------------------

- **プロジェクト固有の秘密は置かない**: 鍵・トークン・個人情報・非公開URLはlegends/にも
  projects/にも置かない。syncに簡易な秘密検査(パターンフィルタ)を仕込む。
- 学びの改版は「追記+出典」で行い、過去の学びを書き換えない(発行済みURLの辞書凍結と同じ考え方。
  誤りだったと分かった学びは、消すのではなく「誤りだった」という学びを重ねる)。
- ライセンスは公開時に決める(道具はコード、学びは文書なので分けて検討)。

## エコシステムの中の位置づけ
-------------------------------------------------------------------------------

- MederuU(器)
  * 学びと道具のハブ
  - anchor(錨)
    * コードに指紋を打つ: 構造指紋(=本人)+位置指紋(=現住所)の二本立て
  - Koushi(格子)
    * 表現力のある表記法: チェックリスト・マトリックスをテキストで管理(`01-koushi-dessin.md`)
  - PAD
    * コードの要約・頭にスッと入る図(コメントも素材にする)(記法の起草は`02-pad-dessin.md`)
  - Okute(奥手)
    * PADの編集(生成と取込)

指紋(錨)->木(PAD)->編集(Okute)は1つの生態系で、KoushiがHTML表現力を、MederuUが器を提供する。
実装順の合意(第40): ①MederuUのデッサン(この文書) -> ②Koushi -> ③PAD/Okute。
