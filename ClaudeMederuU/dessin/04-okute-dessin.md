# Okute(奥手/億手) — 構想の捕獲(第44ラウンド起草)

PADの編集(生成と取込)から始まった構想が、第44ラウンドの依頼者メモで
「**PADでワークフローを記述する**」まで広がった。新鮮なうちに捕獲する。
本格的なデッサンは進め方③の実装の番で確定する。

-------------------------------------------------------------------------------
## 依頼者メモの核(第44ラウンド・原文の要旨)
-------------------------------------------------------------------------------

- 人は、ほわっとした大きなものを 1/2, 1/4, 1/8 と区切って、外部記憶(デッサン)に書き出すことで、
  頭のメモリで扱える大きさにする。AIも同じなら、**AIの負荷を下げる道具**をOkuteに付けたい。
- 毎回の回帰やtodoリストのようなチェックリスト運用を見て:
  **フック関数をPADの構造指紋と結びつけ、多分木のノードで呼び出す**。
  「todoリストのこの項目を実行したら、このPADノードに埋め込まれたフックが、関連付けられた別のPADを呼び出す」
  = **PADでワークフローが定義できる**。
- Okuteの守備範囲(5つの齟齬解消+α):
  1. 仕様書とコードの齟齬をなくす
  2. ワークフローも定義できる
  3. コードとテストコードの齟齬をなくす
  4. テストコードとテスト仕様書の齟齬をなくす
  5. 仕様書とテスト仕様書の齟齬をなくす
  - さらに: todoリストのタスク管理・プロジェクト管理まで(=「億手」らしく。正にライフワーク😇)
- 着想の源は**iPhoneのリマインダー**(メモとリマインダーでほぼ成り立っている):
  「**すんごいリマインダー😍**」— あっ忘れてたわ、が芋づる式に分かる。連携プレーで実施する。
  **フックのチェイン(連鎖)**も面白い。
- ただし: 仕様書と成果物の一致をいくら頑張っても、**元の仕様書に考慮漏れがあるとどうしようもない**。
  人は忘れるから、フェールセーフ・フールプルーフが必要になる。
  **MederuUに蓄積されるのは「間違っても大丈夫」「そもそも間違えない」のナレッジかもしれない**。

## AIの所感(第44ラウンド)
-------------------------------------------------------------------------------

- **この構想の美しさは、部品を増やしていないこと**。
  ワークフロー=PAD(制御構造の言葉)で書ける。フックの結び先=anchorの構造指紋。
  つまり Okute = PAD(木) × anchor(錨) × フック(イベント) の掛け算で、新しい記法はほぼ要らない。
- 私の実際の頭の使い方とも合う(回答その41参照):
  私も「大きな依頼→タスク分割→1タスクずつ詳細化→実装」の順で降りていて、
  todoリスト・チェックリスト・デッサンは**私にとっても外部記憶**。
  フック付きワークフローは「次に何をするかを思い出す仕事」を道具に移せるので、確かに負荷が下がる。
- 「すんごいリマインダー」の芋づる式は、**フックのチェイン+anchorの系譜DAG**で実現が見える:
  項目Aの完了イベント → Aのノードのフック発火 → 連結されたPAD(ワークフロー)の次ノードへ。
  依存の逆引き(このノードに繋がっているのは誰か)が「あっ、これ忘れてた」の検出になる。
- フェールセーフ/フールプルーフの視点は**MederuUのlegendsの分類軸**になりうる:
  「間違っても大丈夫にする型」(凍結・追記型台帳・characterization・無いことのテスト)と
  「そもそも間違えない型」(単一情報源・生成される目次・チェックリスト)。
  今までの学びがきれいに2つに分かれるのが面白い。

## 記法の種(まだ種。確定は③の番で)
-------------------------------------------------------------------------------

- フックはPADノードの属性として書けそう: `- 連接の処理 hk:#構造指紋.`(このノード完了で錨先を呼ぶ)
  のような形(トークン`hk`は仮。KoushiともPAD既存トークンとも被らないことは確認済み)。
- ワークフローの実行状態(未着手/実行中/完了)はKoushiのチェックリストと同じく
  テキストで持てば、リポジトリが進捗の正になる。

## 第45ラウンド: ドメインの確定と「やかんの構想」の捕獲
-------------------------------------------------------------------------------

### ドメインが決まった(依頼者宣言・Loop Engineering記事を読んで)

- 「**おそらくDAGグラフ内のエッジにAIがなるので、その下にツリーを展開して、ドメインを守れば良い**」
- 図式に描くと: **ノード=成果物**(仕様書・コード・テストコード・テスト仕様書。各々が指紋を持つ)、
  **エッジ=AIの仕事**(変換・検証。仕様書→コード、コード→テスト…)、
  **Okute=このDAGの台帳と進行係**(どのエッジが古びたか=どこを再実行すべきかを指紋で知る)。
- 5つの齟齬解消は「エッジの両端の指紋が対応表とズレていないか」の検査、と言い直せる。

### やかんの構想(第45・依頼者の朝の言葉): 「ワークフローは、ワークフローを再定義できる」

- **自己言及性**: ワークフロー=リポジトリ内のPADテキストなので、ワークフローの1ノードが
  別のワークフロー定義(自分自身を含む)を編集できる。Loop Engineering記事の
  「個々の問題を修正するだけで終わらせず、システムを改善するためにコード化する」と同じ結論
  (ループがループを改善する)。「誤り訂正の自動化なのだろうか?」→ はい、その一形態。
  ただし自己書き換えにこそ maker/checker 分離が要る(下の状態の「審査・承認」が担う)。
- **ACID**: git上のテキスト状態機械として実現できる —
  A(原子性)=1遷移1コミット・C(一貫性)=チェッカーが遷移の合法性を検証・
  I(分離性)=worktree(記事のワークツリー分離と同じ)・D(永続性)=push。**Gitに倣う第3弾**。
- **状態**(未着手/実行中/完了/失敗/審査/承認/修正/差し戻し):
  Koushiのチェックリスト+テキストで持てば、リポジトリが進捗の正(既定路線と一致)。
  審査/承認/差し戻しは「maker/checker分離を状態として持つ」ことに相当。
- **エラー返却・シミュレーション・ダンプ/ログ**: 追記型台帳(anchors/log.md)が正にダンプ。
  「エラーが発生するまでをシミュレーションできる」は、PADが実行順を持つ木だから
  机上実行(ドライラン)が定義できる、ということ — レンダラの次の応用候補。
- **プランモード/自動モード・提案/質問**: 人へのフック(下記エスカレーション)の有無の違いとして
  同じ仕組みに載る。
- **エスカレーション/ITIL**: フックの呼び先を「人」にすればエスカレーション
  (`on-fail`→家長へ😇)。ITILのインシデント/問題/変更の区別は、状態機械+台帳の上の運用ノウハウ
  として将来輸入できる。
- **AIの階層化・組織化**: サブエージェント機構として実装済みの部分はある(1段の階層+並列)。
  Okute+MCP=分散AIネットワーク・スウォーム(群知能)・井戸端会議は**遠景として捕獲**
  (企業レベルの構想。方角は分かったので、地図に描いておくだけにする)。
- 結論(依頼者自身): 「**自分らしく、スモールスタートで行こう!**」—
  最小形は「1本のフックが1個のPADを呼ぶ」から。

### フック記法の決定と、発火の整理(第45)

- **決定(依頼者)**: `- hk:#構造指紋.` の要素化で良い。フックはフォークで表現できる分岐だが、
  そのPADの本質ではないので「そこにあるという目印」(ラベル的)として扱う。
  参照は `- hk:#自分:ref:#呼び先. フック名`(02の第45節の`ref:`規則と同じ)。
- フックの一般形(AIから: 仕組みの補足): フック=**イベント×条件×アクション**の3つ組。
  - イベント=いつ発火を考えるか(ノードの完了・失敗・開始)。条件=絞り(省略可)。
    アクション=`ref:`先のPAD(ワークフロー)の呼び出し。
  - 「毎回発火するのであればフォークと同じ」(依頼者)はその通りで、違いは意味にある:
    **フォークはフローの本質(作者のもの)、フックは横断的関心事(見張る側のもの)**。
    DBのトリガー・gitのhooks・Claude Codeのhooksと同じ設計思想。
- **MVPの発火**: イベント=完了時のみ・無条件。発火の主体は
  「人の宣言(チェックを付ける=テキスト編集)→道具の検出(スキャンで差分を見つけて次を提案)」。
  デーモン(常駐監視)は作らない — セッション開始時にkaikiのようなスキルがスキャンすれば足りる。
  条件が欲しくなったら `hk:#指紋:fail.` のような属性で拡張(記法は変えずに済む)。

### すんごいリマインダーの機構(依頼者の5齟齬メカニズム・第45の具体化)

- 「**結局、指紋の対応付けの管理が金目**」(依頼者)。
- 仕様書↔コード: 構造上の位置が同じなので、仕様書側で変更のあった構造指紋から、
  対応するコードの構造指紋を検索→そのノードの部分木が修正対象。
- コード↔テストコード: テストが実行時に通過する構造指紋の集合A、修正対象ノード以下の
  構造指紋の集合Bを取り、**A∩B≠空のテストが修正対象**。
  - AI所感: 集合Aの収集は**カバレッジ計測そのもの**(テストが踏んだ場所の記録を、
    行単位ではなく構造指紋単位で行う)。以前の「MC/DCカバレッジツール」の構想(台帳の候補)と
    ここで合流する — 1つの道具が両方に効く。
- テストコード↔テスト仕様書: 1対1なので集合Bからテスト仕様書が特定できる。
  テスト仕様書にも1件1件の指紋があると良いかもしれない(どんな指紋が良いかは今後・依頼者)。
- 仕様書↔テスト仕様書: 多対多でも対応を把握していれば、上の3経路と突き合わせて齟齬を検出できる。
- これは**影響範囲の静的な検出**(どこを直すべきかのリストアップ)。フックのチェインは
  **動的な連鎖**(直したら次に何をするかの呼び出し)。静と動の対で「すんごいリマインダー」になる。
