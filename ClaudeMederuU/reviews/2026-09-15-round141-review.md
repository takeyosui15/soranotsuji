# レビュー記録 2026-09-15 — 第141ラウンド: ローカルgit復旧の手引き(壊れた参照名「 2」)

依頼(チャット直送・依頼者はコミットできない状態): VSCodeでpushできない。出力ログに
`fatal: bad object refs/heads/claude/inspiring-meitner-oc6gpj 2` /
`did not send all necessary objects` / `ignoring ref with broken name refs/heads/... 2`。

## 診断

- 参照名の末尾に「半角スペース+2」が付いたファイルが、お手元の`.git/refs/heads/claude/`と
  `.git/refs/remotes/origin/claude/`にある。gitはスペースを含む参照名を受け付けないため
  「ignoring ref with broken name」となり、fetchの交渉でその壊れた参照の指すオブジェクトを
  使おうとして「bad object」→「did not send all necessary objects」で中断する(VSCodeの同期は
  push前にfetchするので、pushまで届かない)。
- 「名前 2」はmacOSのFinderの複製、またはiCloud Drive/Dropbox/Google Driveの同期衝突コピーの
  典型。`.git`の中に生えている場合は、リポジトリが同期フォルダ内にある可能性が高い。
- リモートはこちらから確認して健全(`git ls-remote`: 9ブランチ、`claude/inspiring-meitner-oc6gpj`
  は正規に存在=10845c6)。壊れているのはローカルの写しだけ。

## 手順(依頼者のMacで)

1. `find .git -name '* 2' -print` で犯人を確認。
2. `find .git -name '* 2' -type f -delete` で「 2」付きだけ削除(本来の参照は残る)。
3. `git fsck --no-dangling` → `git fetch --prune` → 通常どおりcommit/push。
4. 万一`packed-refs`に「 2」付き行があれば手で削除(`grep ' 2$' .git/packed-refs`)。
5. 再発防止: リポジトリを同期対象外のフォルダ(例: ~/dev/)へ。

## 学び(次の私へ)

- **「did not send all necessary objects」はリモートの罪に見えてローカルの壊れた参照が原因の
  ことがある** — 同じログの先頭にある`bad object <参照名>`と`broken name`を読めば局所化できる。
  リモートの健全性は`git ls-remote`で1発で確かめられるので、先に潔白を証明してから
  ローカルの手当てに入る(依頼者を安心させる順番)。
- **参照名にスペースがあれば、まず同期サービスを疑う** — `.git`内の「名前 2」はほぼ
  Finder/iCloud/Dropboxの衝突コピー。直すだけでなく置き場所の見直しまで案内する。
- **新しい箱では最初に`git log -1`と`git status`** — 作業箱の複製が古い時点に戻っている
  ことがある(今回は1か月半前)。fetch→ff-onlyで先端へ揃えてから書き始める。前ラウンドの
  「台帳は実物を正とする」の作業箱版。
