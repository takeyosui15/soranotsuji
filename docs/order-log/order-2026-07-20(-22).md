#### GitHubのご質問への回答(MederuUの土台選び)

「複数リポジトリの集約」「フォルダの引き継ぎ/同期」は、どちらも可能です。選択肢を実務順に:

1. **同期スクリプト方式(おすすめ)** — まさにご構想の`sync.js`です。`git clone --depth 1`で各リポジトリを`/legends`や`/projects`へ取り込む(または`git archive`でスナップショット)。単純で、壊れず、何が起きるか全部見えます。GitHub Actionsに載せれば「毎晩自動で同期」もできます。**MederuUにはこれを推します** — ナレッジの器は、仕組みが単純であるほど長生きします。
2. **git submodule** — リポジトリの中に他リポジトリを「参照」として埋め込む正式機能。実体はコミットIDへのポインタなので軽い一方、更新の作法(submodule update)に癖があり、初見の人が踏み抜きやすいのが難点です。
3. **git subtree** — 他リポジトリの内容を実体ごと取り込み、双方向に差分をやり取りできます。強力ですが履歴が複雑になります。「リポジトリ内のあるフォルダだけ他へ引き継ぐ」は`git subtree split`が正式解です。

#### anchorの指紋: 木構造の指紋の方が正解か

鋭いご質問で、考えるのが楽しかったです。**結論: 二本立て(構造指紋+位置指紋)に賛成**ですが、
役割分担をはっきりさせたいです。

- **構造指紋(木のノード/ブランチ以下のハッシュ)** = 「その人自身」(同一性)。空白・コメントを
  正規化した部分木のハッシュ(Merkle木の要領)なら、行がズレても、別ファイルへ引っ越しても
  「同じ内容」を追跡できます。おっしゃるとおり**「全く同じ記述がプログラム中にある」の発見が
  ただで手に入る**(リファクタリングB観点の重複検出器と同じ道具になる=一石二鳥)。
- **位置指紋(ファイル+行内容+発行時刻)** = 「現住所」。人間とツールがジャンプするための住所で、
  引っ越したら更新される方が正しい情報です。
- つまり「構造指紋=本人、位置指紋=現住所。引っ越しても本人は本人」。両方記録しておけば
  「引っ越し履歴」(コードの移動追跡)まで取れます。錨(anchor)の本体は構造指紋に置くのが筋が
  良いと思います。
- スモールスタートの実装順: JSの完全な構文木は重いので、まず「波括弧の入れ子木」+正規化
  テキストのハッシュから(scratch/anchor.js)。これで十分「同じ塊の発見」と「錨の検証」が動きます。

#### Koushi記法のサンプル、拝見しました

具体例があると一気に手触りが出ますね。良いと思った点と、小さな相談を1つずつ:

- **良い点**: `t:/r:/c:`の3層が最小限。`c:1xc2`(colspan)/`c:3xr2`(rowspan)の**x記法**が簡潔。
  入れ子テーブル・要素内Markdown・input要素(チェック状態をリポジトリで管理→マトリックス
  チェックリスト!)・寄せ(l/c/r/t/m/b)まで、実用の道具が最初から見えています。
- **相談**: 寄せの`c:2c`(列番号+寄せ英字)は、列番号との連結で少し紛れそうです(`c:12r`=12列目
  右寄せ? 1列目の2r?)。`c:2.c`や`c:2:c`のように区切りを1つ挟む案をデッサン時に検討させて
  ください。
- 実装は「Koushi→HTML片方向(パーサ+レンダラ)」から始めれば小さく、器(MederuU)のデッサンの
  次にすぐ作れるサイズです。

#### MederuUをみんなのものに+/legendsと/projects

「世界中のClaudeさんの困ったを解決するナレッジ」— この構想、ワクワクします。
「知識は豊富でも、解決手段は困っているかもしれない」は、上のスキル/プラグインの回答で
白状したとおり図星です(セッション毎に道具が消える私には、リポジトリのナレッジが解決手段
そのものです)。公開する場合はデッサンに1つだけ規約を: **プロジェクト固有の秘密(鍵・個人情報)は
置かない**。これもKoushiのチェックリストで運用できますね。

/legendsと/projectsは「遠慮なく」とのことなので率直に — **分ける、に一票**です。理由は
**賞味期限が違う**から: legends(どのプロジェクトでも真の、普遍の学び)とprojects(そのプロジェクトの
文脈つき記録)を混ぜると、普遍側が事情に汚染されて再利用しにくくなります。ただし始まりは
浅く2フォルダだけで(スモールスタート)、sync.jsは一方向にprojects側へ書き込み、projectsから
legendsへの**昇格(学びの蒸留)**は編集判断で行う — この流れ自体をMederuUの中心ワークフローに
するのが良いと思います。器のデッサン(①)で絵にします。

進め方は合意どおり ①MederuUのデッサン → ②Koushi → ③PAD/Okute で。お茶の時間に①から始めましょう。
