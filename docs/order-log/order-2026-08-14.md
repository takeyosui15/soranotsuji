#### 1. koushi-dev(開発用リポジトリ)は要るか — 「不要」をおすすめします

結論: 作らなくて大丈夫です。理由は3つ。
1. **開発環境はもう在る**: Koushiの開発の場は宙の辻リポジトリ(tools/koushi.js+vscode-koushi/)で、`takeyosui15/koushi`は「リリースの器」です。つまり開発/本番の分離は、既に「宙の辻側=開発・koushi=公開」という形で成立しています(stagingで組んでから送る流れも、テスト済みのものしか外に出ない関所になっています)。
2. **利用者に届く瞬間は別にある**: 拡張の利用者に変更が届くのはリポジトリのpushではなく`vsce publish`の瞬間です。publishが「本番反映」の関所なので、リポジトリを2つに割る守りは重複になります。
3. **必要になったら枝で足りる**: 将来、外部の協力者が現れて作業が並ぶようになったら、koushiリポジトリ内のブランチ(main+開発ブランチ)で同じことができます。リポジトリを増やすのはその時でも遅くありません。
宙の辻で本番/開発を分けているのは「GitHub Pagesで常に公開されている本番」を守るためでした。koushiは「publishするまで何も公開されない」ので、同じ守りは要らない、という整理です。

#### 2. sample.mdをREADMEへ統合しました(ご提案の通り)

おっしゃる通りにしました。
- READMEの**英語License章の後・日本語章の前**に「Samples / サンプル」章を新設し、結合セル(アイコンの絵)・罫線つき状態遷移表・チェックリスト・input代表4種、の4例を英日の見出しで載せました。

#### 3. 一式の送付 — コミットまで完了・pushで403(あと1クリックです)

`takeyosui15/koushi`の作成、確認しました(空っぽの作り方も手順書通りで完璧でした)。
一式をコピーして初回コミット(README・LICENSE・拡張・レンダラ・文法・テスト・icon=14ファイル)まで作ったのですが、**pushが403(権限なし)で弾かれました**。
原因ははっきりしています: ClaudeのGitHub Appが`soranotsuji-dev`にしかアクセス権を持っておらず、新しい`koushi`リポジトリには「読めるが書けない」状態です(公開リポジトリなので読むのは誰でもできる、の裏返しです)。
**お願い(1クリック+Save)**: GitHubの Settings → Applications → Installed GitHub Apps → Claude の「Configure」→ Repository access に `koushi` を追加してSaveしてください。

#### 4. 「うちのClaudeさん」と「よそのClaudeさん」のPRは区別できるか — できます

良い質問です。答えは「**PRの作者アカウントで確実に区別できます**」。
- 私(たけちゃんのClaude)がPRを出す時は、たけちゃんが許可したGitHub App(上の「Claude」)の名義で、**リポジトリ本体のブランチ**からPRが出ます。
- よそのClaudeさん(=他の誰かが使うClaude)は、その人のGitHubアカウントが作者になり、リポジトリ本体には書けないので**フォークからのPR**になります。
つまり見分け方は2重です: ①作者名(アプリ名義か・他人のアカウントか) ②出所(本体ブランチか・フォークか)。
コミット末尾の「Co-Authored-By: Claude」はどこのClaudeでも似た署名になりますが、あれは「AIが書いた」という印であって、身元はあくまで①②で判定します。なりすましの心配はいりません。

**項目3. 辻ラインの時刻表示の仕様確認**

確認しました。仕様も実装もほぼご認識の通りです。
- 当日線(実線)=「現在日時に最も近い南中」の前後12時間。前日線/翌日線(点線)はその±24時間の窓で、3窓で連続72時間をタイルします。
- 時刻が載るのは当日線だけで、「線上に載る範囲」の5分刻み(分が5の倍数ちょうどの標本)です。
- ただし線が引かれるのは「天体が地平線(観測点標高の伏角込み)より上」かつ「目的点から300km以内」の範囲だけです。

大天井岳→槍ヶ岳で端の方に時刻が無かったのは、不具合ではなく幾何学的な現象でした。
遠距離側では地球の曲率が支配的になり、天体高度1°の変化で線が約200kmも走ります。
月の高度変化は5分で約1°なので、最後の5分刻みの時刻から線の端までの間に、100km級の「時刻なし区間」ができます。
このまばら地帯が始まる距離の目安は √(2×地球半径×観測点と山頂の標高差) です。
富士山(平地からの標高差約2800〜3776m)なら約190〜220km先=300km制限の直前なのでほぼ全域に時刻が載りますが、大天井岳(2922m)→槍ヶ岳(3180m)は標高差約260mなので、約57kmから先がまばらになります。
つまり「槍ヶ岳は山頂が富士山に比べると低いので」というたけちゃんの推測は本質的に正しくて、正確に効いているのは山頂の絶対高度ではなく「観測点と山頂の標高差」です。
(時刻ラベルは重なっても間引かない設定なので、表示が消されているのではなく、その区間に5分刻みの標本が落ちていないだけです。)

**項目6. チェックボックス化と±反転**

チェックボックス化(「:天の川オプション」の流儀で前にチェック)は賛成です。
オンオフが1タップになり、他の項目の流儀とも揃います。
±反転も「夏の天の川を上から見て時計回り」という直感に合わせる方向に賛成ですが、1点だけ設計の注意があります。
符号の意味を変えると、保存済みデータ・共有URL・CSV・verify143の「向きの凍結標本」の互換が絡みます。
おすすめは「内部値と保存形式は現行のまま、画面の表示・入力だけ反転する」方式です(互換問題ゼロで、見た目だけ直感に合わせられます)。

理由は、行ヘッダの「ID:0☆🔛」の並びに1文字で収まりスペースを取らないこと、⭐️そのものが状態表示を兼ねるので説明が要らないことです。

**項目15. PlusCode入力**

無料で実現できます。
PlusCode(Open Location Code)はGoogleが公開しているオープンな仕様+参照実装(Apache-2.0)で、フルコード(例: 8Q7XMQPJ+2V)の復号は約100行の純JavaScriptです。
通信もAPIキーも不要で、オフラインで座標に変換できます。
実装案: 観測点/目的点の緯度経度欄でPlusCodeの形(専用アルファベット20文字+「+」)を検出したら復号して座標にします(既存の「緯度,経度」直入力・地名検索と共存)。
1点だけ制約: 「MQPJ+2V 港区」のような短縮形は基準地名の解決が必要ですが、これも既存の地名検索(GSI/OSM)と組み合わせれば無料のままいけます。
まずはフルコード対応から入れるのが良いと思います(第84候補)。

**項目19. 海外旅行時のタイムゾーン挙動**

整理するとこうなります。
- ブラウザの時刻とタイムゾーンはOSの設定に従います。SIMは直接は関係ありません。
- ただしスマホは既定で「日時を自動設定」がオンなので、現地の携帯電話網(海外SIMでもローミングでも)や位置情報から自動で現地タイムゾーンへ切り替わります。
  結果として「日本から持って行ったスマホでも、ブラウザは現地時間を返す」が実用上の答えです。
- 自動設定をオフにしていれば日本時間のままです(この場合、項目18の切替も働かず、GSI優先のままです)。
- 宙の辻の計算は「端末の時計のその瞬間+緯度経度」が基準なので、端末が現地時間なら結果の時刻表示も現地時間になります(天文計算は絶対時刻ベースのため、どちらの表示でも同じ瞬間を指します)。

分かりやすい表示のご提案: 日時情報メニューの近くに「タイムゾーン: Asia/Tokyo (UTC+09:00)」を常時表示し、日本以外の時は「地名検索はOSM直行」の注記を添える+ヘルプに「海外での利用」の節を設ける、を項目19の実装(第84候補)として考えています。
表示の場所や文言にご希望があればお聞かせください。

#### 1. 非同期並行処理の同類監査(ご依頼)

おっしゃる通り「こういう時でないと見つからない」類でした。
アプリ内の世代カウンタ11箇所(辻検索・辻メッシュ・辻ライン・辻ライン365・My辻一括/File・標高取得・地形・都市ビル・再生・宙断面)を全て開き、「待つ側(awaitの続き)が照合しているか」を1つずつ確認しました。
結果: 8箇所は照合済みで健全、**3箇所に同類の穴があり、修正しました**。

**穴1: 可視判定ポップアップ自身のawait(第78修正の続きの穴)**。
第78の修正で「取得完了後の照合」は入れましたが、その後に呼ぶ可視判定(showVisibilityResult)の内部にもう1つawait(判定用のタイル取得)があり、判定中に宙の窓へ切替るとポップアップが出る余地が残っていました。

**穴2: 観測点/目的点の非同期設定の追い越し**。
地図クリック・地名確定・GPS・高移は「標高を取得(await)してから座標+標高を書き込む」ため、素早く2回操作すると、遅い方の取得が後から解決して古い地点で上書きする競合がありました(地図を2回クリック→1回目の地点に戻る等。高移はスキャンに数秒かかるので特に窓が広い)。
チケット方式(_locSetSeq)を入れ、各操作は開始時に番号を取り、await後に自分がまだ最新の操作の時だけ書き込むようにしました。
同期の設定操作(Hom/推山・My観測点/My目的点の位置反映)も番号を進めるので、進行中の古い取得はそこで無効になります。
verify146のA1で「遅いクリックA→速いクリックB→Bが勝つ」を凍結しています。

**穴3: 宙断面の取得中に閉じた後の書き戻し**。
雲量取得(await)の間に宙断面を閉じると、取得済みデータが閉じた後にキャッシュへ書き戻され、すぐ開き直した時に古い地点の雲が出る余地がありました。
閉じるたびに進む世代(_sdGen)で、取得中に閉じられた場合は書き込まないようにしました。

小さな備忘(修正対象外とした軽微2件): My観測点/My目的点の行内で座標を素早く2回変えると標高だけ古い方になる余地(行単位・実害が小さい)と、気象取得ボタンの連打で後から解決した方が勝つ件(操作自体が明示的)は、監査記録に留めました。
