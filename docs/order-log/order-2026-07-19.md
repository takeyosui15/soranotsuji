#### 11+18. 動画の破損とカクカク(原因究明+録画方式の刷新)

「スマホのどのアプリでも再生不可」という症状から、**その端末でのVP9ソフトウェアエンコードが実時間録画に追いつかず破綻している**可能性が濃厚です(スマホのハードウェアエンコーダは通常H.264のみで、VP9は高解像度だとCPU任せになるため)。3つの対策を実装しました。

- **フレーム同期録画方式に刷新**(ご提案の「処理を溜めてから消化する」に相当): 従来は実時間で録画しながら1/fps秒毎にフレームを描いていたため、描画が間に合わない端末ではコマ落ちして「カクカク」になっていました。新方式は「1コマ描き終えた瞬間だけフレームを流し(requestFrame)、描画中は録画タイムラインを一時停止(pause)」します。**描画がどれだけ遅くても全コマが等間隔で記録されます**。検証実測: 描画に11.5秒かかる環境でも、生成動画は正しく2.0秒(10コマ/5fps)・全コマ入りでした。エンコーダの負荷も均されるため、スマホの破綻の抑制も期待できます。
- **生成後の自己検証**: 書き出し/再生用の動画を生成した直後に、その端末で再生可能かを自動チェックし、壊れていた場合は「MP4か小さい出力サイズをお試しください」(書き出し)/「アニメーション再生をご利用ください」(再生)と具体的に案内します。

#### 11+18. 動画: スマホChromeで開けない/YouTubeアプリで0秒→クラッシュ(調査+診断機能の追加)

状況の切り分けです。前回のフレーム同期録画+Durationパッチで「Mac miniでは正常に開けて長さも出る」ようになった一方、スマホ側で開けない・0秒表示という症状は、**ファイル側ではなく再生側(Androidのパーサ)の問題である可能性が高い**と考えています。

- Macの再生系(QuickTime/ブラウザ)はWebMの解釈が寛容ですが、AndroidのMediaExtractor(YouTubeアプリやスマホChromeのファイル再生が使う低レベルパーサ)は厳格で、MediaRecorderが出力するストリーミング形式のWebM(Cluster構造・キューポイントなし)を「長さ不明(0秒)」と判定したり、開けないことがあります。0秒表示→次へ進むとアプリが落ちるのは、YouTubeアプリがdurationを0とみなしたまま処理を続けた時の既知の挙動と一致します。
- そこで今回、**書き出し完了時に「出力診断」を約15秒表示する機能**を追加しました。実際のMIME(コーデック)・ファイルサイズ・**書き出した端末自身がメタデータから読み取れた再生時間**・自己検証結果を表示します。ここで「メタデータ長 25.00秒」のように出ていれば、ファイルには長さ情報が正しく入っている=再生側の対応の問題、と切り分けられます。
- お願い: スマホでの用途には**出力フォーマット「:H.264 8-bit(MP4)」**をお試しください。MP4(H.264)はAndroidのハードウェア再生パスに乗るため、スマホChrome/YouTubeアプリとも最も互換性が高い形式です。MP4で書き出した場合の (1)スマホChromeで開けるか (2)YouTubeアプリで長さが出るか、と、WebMの場合の出力診断の表示内容(特にメタデータ長)を教えていただけると、次の一手(例: WebMへのCues(シーク索引)後付け)を判断できます。


## ① 気圧面の7変数

`/v1/jma`（および汎用`/v1/forecast`）で取れる気圧面変数は以下の7つで、変数名は`{変数}_{気圧面}hPa`の形式です。

1. **temperature**（気温、°C）
2. **relative_humidity**（相対湿度、%）
3. **dew_point**（露点温度、°C）— 気温との差（湿数）が雲の出やすさの指標になります
4. **cloud_cover**（雲量、%）— ただし注意点あり、後述
5. **wind_speed**（風速）
6. **wind_direction**（風向、°）
7. **geopotential_height**（ジオポテンシャル高度、m）— その気圧面が実際に海抜何mにあるか

選べる気圧面は1000 hPa（約110m）から975、950、925、900、850（約1500m）、800、700（約3km）、600、500（約5.6km）、400、300（約9.2km）、250、200、150、100 hPa（約15.8km）までの16面です。この高度はあくまで目安で、気圧配置によって変動するため、正確な高度はgeopotential_heightで取得します（海抜であって地上からの高さではない点に注意）。

URLはこんな形になります：

```
&hourly=cloud_cover_850hPa,relative_humidity_850hPa,temperature_850hPa,
        dew_point_850hPa,wind_speed_300hPa,geopotential_height_850hPa
```

宙検索の設計上、押さえておきたい注意点が3つあります。まず、JMAモデルは気圧面ごとのパラメタライズされた雲量を直接提供していないため、Open-Meteoが相対湿度からSundqvist et al. (1989)の手法で近似しており、低・中・上層雲量の変数とは完全には一致しないことがあります。つまり**スコア計算の主役はあくまで`cloud_cover_low/mid/high`（これはMSMの正規プロダクト）**で、気圧面データはSCW風の高度断面の可視化や詳細分析用と位置づけるのが正解です。次に、MSMの気圧面データは約11km格子・3時間刻み・4日分で、地上変数（5km格子・1時間刻み）より粗くなります。最後に、`elevation`パラメータで観測点の標高を明示指定できる（デフォルトは90m DEMによる標高ダウンスケーリング）ので、山頂の観測点では山頂標高を渡すと精度が上がります。

面白い使いどころとしては、850hPaの湿数（T−Td）が小さければ下層が湿っていて雲が湧きやすい、300hPa付近の風速が強ければジェット気流直下でシーイング悪化傾向、といった推定ができます。また観測点標高が950hPa面より上なら「眼下は雲海、頭上は快晴」という星屋にとって最高の状況も検出できます。

## ② IndexedDBにサーバーは不要です

IndexedDBは**ブラウザに内蔵されているクライアントサイドのデータベース**なので、サーバーサイドのスクリプトは一切不要です。GitHub Pagesの静的ホスティングのまま、宙の辻の完全クライアントサイド構成を崩さずに使えます。localStorageとの違いは、非同期API・大容量（一般に数百MB規模まで、ディスク容量依存）・JSオブジェクトをそのまま保存できる点で、「地点×168時間×複数変数」の予報JSONを貯めるのに向いています。

最小実装はこんな感じです：

```js
const dbReady = new Promise((ok, ng) => {
  const req = indexedDB.open('soranotsuji-wx', 1);
  req.onupgradeneeded = () => req.result.createObjectStore('fc');
  req.onsuccess = () => ok(req.result);
  req.onerror = () => ng(req.error);
});

const idb = async (mode, fn) => {
  const db = await dbReady;
  return new Promise((ok, ng) => {
    const r = fn(db.transaction('fc', mode).objectStore('fc'));
    r.onsuccess = () => ok(r.result);
    r.onerror = () => ng(r.error);
  });
};

const TTL = 2 * 3600e3;  // MSMは3時間毎更新なので2時間で失効
async function getForecast(lat, lon) {
  const key = `jma:${lat.toFixed(2)},${lon.toFixed(2)}`;
  const hit = await idb('readonly', s => s.get(key));
  if (hit && Date.now() - hit.t < TTL) return hit.data;
  const url = `https://api.open-meteo.com/v1/jma?latitude=${lat}&longitude=${lon}`
    + '&hourly=cloud_cover_low,cloud_cover_mid,cloud_cover_high&timezone=Asia/Tokyo';
  const data = await (await fetch(url)).json();
  await idb('readwrite', s => s.put({ t: Date.now(), data }, key));
  return data;
}
```

キー設計のコツは、座標を小数2桁程度に丸めてキャッシュヒット率を上げること（MSMは5km格子なので、それより細かい座標の違いは同じ格子に落ちます）。TTLはMSMの更新周期が3時間毎なので2〜3時間が目安です。iPhoneのSafariは長期間使わないとサイトのストレージを削除することがありますが、これはキャッシュなので消えても再取得するだけで実害はありません。

ちなみにGoogle Drive同期の設計（クライアントサイドのみ・手動同期）と同じ思想で、キャッシュも端末ローカルで完結し、同期対象にする必要はない、という整理で良いと思います。観測点リストは同期、予報キャッシュはローカル使い捨て、ですね。

```js
map.addLayer({
```
