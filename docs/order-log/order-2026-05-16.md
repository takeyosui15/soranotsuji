### 回答 (2026-05-16) — 辻検索◎と辻ラインのズレの分析と修正

具体的なデータをいただきありがとうございます。分析の結果、`toFixed()` の丸めではなく、**2つの本質的な問題**が原因と特定しました。

#### 問題1: 辻検索の精度計算が「擬似ユークリッド」だった (球面角距離ではなかった)

辻検索 Worker の `angularDistance`:

```js
// 旧 (擬似ユークリッド = 平面距離):
function angularDistance(az1, alt1, az2, alt2) {
    let azDiff = az1 - az2;
    azDiff = ((azDiff + 540) % 360) - 180;
    const altDiff = alt1 - alt2;
    return Math.sqrt(azDiff * azDiff + altDiff * altDiff);  // ← 球面の歪みを無視
}
```

これは天空を平面とみなしたユークリッド距離で、高度が低いほど方位角の単位距離が cos(alt) で縮む球面性を無視していました。

**修正**: 厳密な球面角距離 (asin/acos の球面三角公式) に置換:

```js
function angularDistance(az1, alt1, az2, alt2) {
    const toRad = Math.PI / 180;
    const sinDelta = Math.sin(alt1*toRad) * Math.sin(alt2*toRad) +
                     Math.cos(alt1*toRad) * Math.cos(alt2*toRad) * Math.cos((az1-az2)*toRad);
    return Math.acos(Math.max(-1, Math.min(1, sinDelta))) * 180 / Math.PI;
}
```

Diamond Fuji は高度約 3° なので影響は小さい (cos(3°) ≈ 0.9986) ですが、原理的に正しくなります。

#### 問題2: 辻ラインの 5秒サンプリングが視覚的ズレの主因

辻検索◎ 0.12° の物理的な意味:
- 観測点 (府中本町駅) から見た天体と目的点の合成角度差が 0.12°
- 例: 方位差 0.10° + 高度差 0.07° (合成 0.12°) など
- 100km 地点での観測点位置のズレに換算: **約 213m** (角距離 × 距離 × π/180)
- ◎ 境界 (218m) のぎりぎり内側 → ◎判定 ✓

しかし辻ラインの中心線 (実線) を **5秒間隔でサンプリング** していたため:
- 太陽方位角速度 0.0042°/秒 × 5秒 = 0.021° → 観測点位置で約 37m のズレ
- これが視覚的に「府中本町駅から最寄りの線分」を真の中心線から約 37m ずらして表示
- 結果: 府中本町駅が ◎境界 (218m) の **外側** に見える

#### 修正内容

1. **`tsuji-search-worker.js`**: 角距離を球面角距離に変更
2. **`script.js` (`updateDPLines`)**: 辻ラインのサンプリングを **5秒 → 1秒** に戻す
3. **`index.html` ヘルプ**: 「5秒間隔・約30m刻み」→「1秒間隔・約5〜7m刻み」に修正

#### サンプリング 1秒に戻すことについて

前回 5秒に変更したのは負荷軽減のためでしたが、その後の以下の最適化で十分軽量化されています:
- Worker プール (起動コスト削減)
- 緯度依存 Reff (キャッシュ可)
- Vincenty Direct 自前実装 (CDN不要)
- 局所半径バグ修正済 (旧3697km → 6371km、計算量も適正化)

「測量レベル」を達成するため、1秒に戻すのが最善の判断です。もし負荷が気になる場合は、また別の最適化 (例: アニメ中だけ 5秒) でバランスを取りましょう。

> **辻ラインと辻検索の精度記号の違い:** 辻ラインの◎/○/△バンドは「**方位角のオフセット**のみ」で定義されていますが、辻検索の精度角距離は「方位差²+高度差²の合成 (球面角距離)」です。辻ラインは観測位置の**目安**としてご活用ください。正確な判定は辻検索の精度角距離に基づきます。

#### 3. WebGPU による並列化について — 率直な見解

**結論: 現状の Web Worker プールが天体計算に対しては最適解**であり、WebGPU は不向きと判断します。理由を説明します。

##### WebGPU が向いている処理
- 画像処理 (ピクセル単位の同一処理)
- 機械学習 (行列演算)
- 物理シミュレーション (パーティクル、流体)
- **共通点: 「大量データに対して同じ短い処理を繰り返す」**

##### 天体計算 (辻検索/辻ライン) の特性
- **Astronomy Engine** は 1回の `Equator/Horizon` 呼び出しで:
  - VSOP87 惑星位置モデル (数百項の三角級数)
  - 歳差・章動・光行差補正
  - ケプラー方程式の反復解法
  - 屈折補正
- これらは **条件分岐** + **反復計算** + **テーブル参照** = GPU シェーダー (WGSL) には移植困難
- GPU は分岐が多い処理が苦手 (ワープ発散)

##### WebGPU を使うなら必要な作業
- Astronomy Engine の全ロジック (~数万行) を WGSL シェーダー言語で書き直す
- VSOP87 の数百の三角級数係数をバッファで渡す
- ケプラー方程式の反復解法を固定ループに変換
- **実質的に Astronomy Engine を GPU で一から再実装** — 数ヶ月〜年単位の作業

##### 現状の Web Worker プールの利点
- Astronomy Engine をそのまま使える (コード共有)
- `navigator.hardwareConcurrency` 個のプールで論理コアフル活用 (現状8並列)
- Worker 間通信は `postMessage` (低オーバーヘッド)
- DP線 Worker: 反復補正 + Vincenty Direct を含む複雑なロジックも実行可能

##### もし更に高速化するなら (WebGPU ではなく)
1. **SharedArrayBuffer + Atomics**: Worker 間の高速通信 (postMessage のコピーコスト削減)
2. **Worker 数の増加**: 現状 `Math.min(hardwareConcurrency, 8)` の上限を `16` に引き上げ
3. **WebAssembly**: Astronomy Engine を Rust/C++ で再実装して WASM 化 (2-5x 高速)
4. **適応的サンプリング**: 辻ラインの可視時間帯のみ精密計算 (既に粗スキャンで実装済)
5. **DP線365**: 1日単位の更なる分割 (前半/後半) — ご提案の通り、`hourStart/hourEnd` のチャンク分割を 6時間単位にすることは可能

##### 現在の実行速度の見積もり

| 処理 | 計算量 | 現状の実行時間 (8 Worker) |
|---|---|---|
| 辻ライン (3日×3天体) | ~86400秒×5秒刻み×3天体 ~52000点 | < 2秒 |
| 辻検索 (1年×5天体) | ~365日×1440分×5天体 ~2600000分 | < 30秒 |
| 辻ライン365 (365日×3天体) | ~365日×1440分×3天体 | < 3分 |

十分実用的な速度に達していると思います。もし特定の処理がまだ重いと感じるようでしたら、具体的にお知らせください。Worker の分割単位の調整等で対応します。

### 回答 (2026-05-16) — 表示天体レイアウト + 方位日本語 + Worker数32 + SharedArrayBuffer

#### 1. 表示天体の方位を日本語で表示

16方位の日本語変換ヘルパー `azimuthToDirectionJP` を追加:

```js
function azimuthToDirectionJP(azDeg) {
    const dirs = ['北','北北東','北東','東北東','東','東南東','南東','南南東',
                  '南','南南西','南西','西南西','西','西北西','北西','北北西'];
    return dirs[Math.round(((azDeg % 360) + 360) % 360 / 22.5) % 16];
}
```

ID行に「方位 東南東」を動的表示:

```
太陽
ID: Sun / 方位 東南東
方位角 313.2795° / 視高度 -19.6782°
出時刻 04:43:07 / 入時刻 18:44:15
南中時 11:43:28 / 視半径 0.264°
赤経 3.552663h / 赤緯 19.163396°
```

#### 2. 表示天体のレイアウト入れ替え

旧順序: ID → 赤経赤緯 → 出入時刻 → 南中/視半径 → 方位角/視高度
新順序: **ID/方位 → 方位角/視高度 → 出入時刻 → 南中/視半径 → 赤経赤緯**

方位角/視高度を最上位 (よく見る情報) に、赤経赤緯を最下位 (詳細情報) に移動。表示天体リストとMy天体リストの両方を変更。

#### 3. Worker 数上限を 8 → 32 に引き上げ

```js
// 旧:
const DP_POOL_SIZE = Math.max(1, Math.min(navigator.hardwareConcurrency || 4, 8));
const TSUJI_NUM_WORKERS = Math.max(1, Math.min(navigator.hardwareConcurrency || 4, 8));

// 新:
const DP_POOL_SIZE = Math.max(1, Math.min(navigator.hardwareConcurrency || 4, 32));
const TSUJI_NUM_WORKERS = Math.max(1, Math.min(navigator.hardwareConcurrency || 4, 32));
```

将来の多コア CPU (16コア、32コア) に対応できます。現在のPCでは `navigator.hardwareConcurrency` の値 (通常 4〜16) がそのまま使われるので、無駄な Worker は作られません。

#### 4. SharedArrayBuffer について — 注意点

SharedArrayBuffer を使うと Worker 間で高速なゼロコピー通信が可能ですが、**重要な前提条件**があります:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

これらの **HTTPヘッダーがサーバー側で必要**です (Spectre 脆弱性対策として、ブラウザが必須としている)。

| 環境 | SharedArrayBuffer |
|---|---|
| soranotsuji.net (自前サーバー) | ✓ HTTPヘッダー設定可能 |
| GitHub Pages | ✗ ヘッダー設定不可 |
| Netlify | △ _headers ファイルで対応可 |
| VSCode Live Preview | ✗ |

さらに、COEP (`require-corp`) を有効にすると、**外部CDNからの全てのリソース** (`<script>`, `importScripts`, `<img>` 等) に `crossorigin` 属性が必要になり、CORS 非対応の CDN (例: sourceforge の GeographicLib) が読み込めなくなります。

**現時点の推奨**: SharedArrayBuffer の導入は、サーバー環境の確認と COEP 対応 (全外部リソースの crossorigin 対応) が完了してからが安全です。Worker 数 32 化だけでも十分な並列化向上が見込まれるため、まずはこちらで効果を確認してください。

将来的に SharedArrayBuffer を導入する際は:
1. サーバーの HTTP ヘッダー設定
2. 全 `<script>` に `crossorigin="anonymous"` 追加
3. GeographicLib を自前ホストに変更 (sourceforge は CORS 非対応の可能性)
4. Worker の postMessage を SharedArrayBuffer ベースに変更

の手順で対応します。

# 🎉 宙の辻 v1.20.0 リリース — 測量レベルの精度を目指して

v1.19.2 から大幅な精度向上と機能拡張を行いました。特に、辻ラインと辻検索の計算精度を **WGS84 楕円体ベース** で見直し、~1000m あった系統誤差を < 1mm に解消しました 🎯

## 🔧 不具合修正

### 辻ライン位置精度の劇的改善 (TT-富士山 で ~1000m → < 数m)

複数のバグと近似誤差が積み重なって、辻ラインが目的の観測点から最大 1000m 以上ズレていました。以下の修正で **測量レベルの精度** を達成:

- **子午線収差バグ修正**: `body_az + 180°` の平面近似で観測点位置を求めていたため、WGS84 楕円体上の back-azimuth との誤差で TT-富士山で **~1000m の南東ズレ**。Newton 反復法で正確な back-azimuth を求めるよう修正。
- **`getLocalEarthRadius` の公式バグ**: 赤道で地球半径が約 2,525km と半分以下の値になっていた数式エラー。WGS84 楕円体の正しい geocentric radius 公式に修正。
- **気差計算の R/Reff 混在**: 三角形の各辺で素の地球半径 R を使い、距離計算だけ Reff (= R/(1-k)) を使う不整合で、TT-富士山 (気差 ON) で **~9km の過大評価**。全て Reff に統一。
- **月の視差・観測点固定誤差**: Worker 内で観測点位置を反復補正 (最大 3 回) して、月の topocentric 視差と固定位置誤差を解消。
- **距離計算の鋭角/鈍角解バグ**: 観測者が高い場合 (山頂から下を見る)、`asin` の鋭角解で偽の遠方解を返していた。鈍角解に修正 (4,133km の誤差 → 0m に)。
- **視高度と距離の双方向整合性**: 近似式から厳密三角形解 (atan2 版) に置換し、`calculateDistanceForAltitudes` との往復誤差を **0.00m** に。

### 辻検索の精度向上

- **角距離を球面角距離に**: 旧版は天空を平面とみなしたユークリッド距離。球面角距離 (acos 形式) に修正。
- **calculateBearing を WGS84 化**: 球面三角法 → WGS84 楕円体ベース。TT-富士山で 0.08° (≈ 太陽の **19秒** 分の時刻精度) 改善。
- **距離計算を WGS84 化**: `L.latLng().distanceTo()` (球面 Haversine) → GeographicLib の `Inverse` で 61m 改善。

### その他の不具合修正

# 宙の辻 v1.20.0 リリースのお知らせ

宙の辻 v1.20.0 をリリースしました。本バージョンでは、辻ラインと辻検索の **位置精度を測量レベル (誤差 数m以内)** まで引き上げ、新機能の追加と表示の整理を行いました。

## ⚠️ ご利用前にお読みください

新機能・新仕様により、これまでと挙動が変わる箇所がございます。誤った結果と取られないよう、以下の点をご確認ください。

### 辻ラインの精度記号と辻検索の精度記号は意味が異なります

辻ラインの **◎/○/△ の境界線** は、観測点から見た **天体の方位角ずれのみ** で描かれた目安線です。一方、辻検索の **◎/○/△ の精度角距離** は、**方位角ずれ と 視高度ずれ の合成 (球面角距離)** で判定しています。

両者は本質的に異なるため、辻検索で「◎」と判定された日でも、辻ライン上では破線 (◎境界) のすぐ外側に観測点が描画されることがあります。**位置精度の正確な判定は辻検索の結果を基準としてください**。辻ラインは観測位置の目安としてご活用ください。

### 辻ライン365 は起動時に常に OFF となります

辻ライン365 は計算量が大きいため、ブラウザ起動時には常に OFF の状態で始まります。前回 ON の状態でブラウザを閉じても、再起動時には自動再開しません。観測点・目的点・日付を変更した場合は、**辻ボタンを一度 OFF にしてから再度 ON** にすることで最新の状態で再計算されます。

### 標高グラフの可視判定について

可視判定 (OK/NG ポップアップ) は、観測点高・目的点高を加えた直線と地形の比較のみで行います。**大気の屈折と地球曲率は考慮していません**。遠距離の見通し判定では実際と異なる場合がありますのでご注意ください。

## 主な変更点

### 不具合修正

#### 位置精度の大幅向上

辻ラインが目的の観測点から最大 1km ほどずれる現象がありました。複数の計算上の不整合と近似誤差を見直し、**WGS84 楕円体ベースで誤差 数m 以内**まで精度を改善しました。

具体的に解消した不整合・誤差:
- 観測点位置を求める際の方位反転で、平面近似を使用していた点 (子午線収差: 約 1000m)
- 気差計算における素の地球半径と有効地球半径の混在 (高度角依存で最大 ~9km)
- 観測点緯度における地球半径計算式の誤り (赤道で約 半分の値)
- 月の視差や観測点固定による誤差 (約 25m × 2)
- 視高度と距離の双方向計算における近似誤差 (~3km)
- 観測者が高い場合の距離計算における鋭角解・鈍角解の誤選択 (山頂運用時に大きな誤差)

これにより、**東京タワー・府中本町駅から富士山へのダイヤモンド富士、パール槍ヶ岳の山頂運用** など、これまで数百m〜数km ずれていたケースで、数m 以内の精度で観測位置を求められるようになりました。

#### 辻検索の時刻精度向上

辻検索の基準方位角・距離計算を **WGS84 楕円体ベース** に統一しました。これにより、太陽の方位差 0.08° 相当 (時刻にして 約 19秒) の系統誤差が解消されました。

#### その他の修正

- My辻検索の進捗バーが正しく表示されない問題を修正
- 一括計算ボタンと File取得ボタンが同時実行された場合の挙動を排他トグル化
- 辻ライン365 のブラウザ再起動時の描画不具合を修正
- 入力欄のオートコンプリートを全面的に無効化 (天体ID欄に意図しない初期値が入る問題)
- ヘルプ記載の誤記 (辻検索の結果上限、許容範囲の初期値など) を修正
